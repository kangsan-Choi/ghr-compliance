2. /agents로 에이전트를 만드는 실제 방법 Creating Subagents

Claude Code에서 서브에이전트는 「지침이 담긴 Markdown 파일 1개 = 에이전트 1개」입니다. 대화가 아니라 파일로 존재합니다.

2-1. /agents 대화형 마법사로 생성

Claude Code 프롬프트에 슬래시 명령을 입력하면 생성 마법사가 뜹니다.

> /agents
# 메뉴가 열림:
#   1. Create New Agent   ← 선택
#   2. 저장 위치 선택:  Project (.claude/agents/)  또는  Personal (~/.claude/agents/)
#   3. 무엇을 하는 에이전트인지 자연어로 설명  →  Claude가 초안(이름·설명·시스템프롬프트)을 자동 생성
#   4. 사용할 도구(tools)·모델(model) 선택
#   5. 저장  →  .claude/agents/<이름>.md 파일이 만들어짐

이 프로젝트에서는 이 과정을 7번 반복해 .claude/agents/ 폴더에 7개의 .md 파일을 만들었습니다.

2-2. 만들어진 파일의 구조 — Frontmatter + 시스템 프롬프트

생성된 파일은 위쪽 YAML frontmatter(메타데이터) + 아래쪽 본문(시스템 프롬프트 = 역할 지침)으로 구성됩니다. 아래는 실제 labor-law-researcher.md의 구조입니다.

.claude/agents/labor-law-researcher.md
---
name: labor-law-researcher              # 에이전트 호출 이름
description: "...일본 노동법 개정 알려줘 → 이 에이전트 사용..."  # 언제 부를지 + 예시
model: sonnet                            # 이 에이전트가 돌릴 모델
memory: project                          # 프로젝트 범위 영구 메모리 부여
---

You are an elite international labor law research specialist...   # ↓ 여기부터 본문 = 역할·행동 지침

## Core Mission
Research and present the latest labor laws and amendments for any specified country...

## Research Methodology
### Step 1: Identify the Target Country ...
### Step 2: Conduct Web Searches
- "[country] labor law 2025 2026 amendment"
- "[country] minimum wage 2026" ...
## Output Format
### 🏛️ [Country] Labor Law Summary
**법령명:** ... **최근 개정일:** ... **관할 기관:** ...

frontmatter가 하는 일 (기계가 읽음)

name·description는 오케스트레이터가 "이 일은 누구에게 시킬지" 자동으로 고르는 근거입니다. description 안의 사용 예시가 라우팅 정확도를 높입니다. model·memory는 실행 환경을 정합니다.

본문이 하는 일 (에이전트가 읽음)

본문 전체가 그 에이전트의 시스템 프롬프트입니다. 여기에 미션·조사 방법·출력 포맷(스키마)·품질 기준을 못 박아 두면, 매번 같은 형태의 결과가 나옵니다. 데이터 파이프라인의 핵심입니다.

핵심 아이디어 — 각 에이전트에게 "입력을 어떻게 받고 → 무슨 역할을 하고 → 어떤 형식으로 출력하라"를 본문에 명확히 적어두는 것이 전부입니다. 출력 형식을 표준화했기 때문에, 앞 에이전트의 출력이 뒤 에이전트의 입력으로 그대로 연결(pipe)됩니다.

3. 7개 에이전트의 입력·역할·출력 Agent Roster

각 에이전트를 「무엇을 입력받아(IN) · 무슨 역할을 하고(ROLE) · 무엇을 내놓는지(OUT)」로 정리했습니다. 실제 .claude/agents/에 존재하는 파일들입니다.

🎯 compliance-orchestrator 지휘자

전체 파이프라인을 정해진 순서로 지휘하고, 하위 에이전트 결과를 모아 최종 산출물을 만드는 총괄.

IN사용자 요청("한국·일본 컴플라이언스 리포트 만들어줘")과 대상 국가 목록 ROLE국가 확정 → 4개 하위 에이전트를 순서대로 dispatch → 결과 취합 → 대시보드/데이터 생성 (자세히는 §4) OUT국가별 통합 결과, data/*.json 및 인터랙티브 HTML

🏛️ labor-law-researcher 조사

국가별 최신 노동법·개정·최저임금·근로시간을 웹에서 조사해 출처와 함께 표준 형식으로 정리.

IN대상 국가명(한국어/영어 무관) ROLE정부 관보·ILO·노동부·대형 로펌 가이드를 web_search로 교차조사(2~3개 출처), 공포일 vs 시행일 구분 OUT근로시간·휴가·해고·급여·사회보험 등 카테고리별 요약 + 최근 개정 타임라인 + 출처 URL

🗂️ hr-policy-structurer 구조화

회사의 HR 제도(근로시간·휴가·급여·해고·복리후생)를 다운스트림 비교가 가능한 표준 JSON으로 변환.

IN자연어로 기술된 현행 HR 제도("주 52시간, 연차 15일...") ROLE카테고리별로 파싱·검증하여 스키마에 맞춰 정규화 (개인정보는 제외) OUT갭 분석기가 바로 소비할 수 있는 구조화된 정책 JSON

⚖️ compliance-gap-analyzer 비교

법정 기준(조사 결과) vs 현행 제도(구조화 결과)를 항목별 비교해 갭을 판정.

INlabor-law-researcher 출력 + hr-policy-structurer 출력 ROLE항목별 대조 → 🔴긴급 / 🟡권고 / 🟢준수로 상태 부여 + 근거 조문 + 개선 권고·우선순위 OUT갭 목록(항목·상태·근거·권고). 이 로직이 나중에 rules.py로 코드화됨

📋 gap-analysis-reporter 리포트

갭 분석 결과를 경영진용 구조화 리포트(요약·긴급·권고·참고)로 정리.

IN갭 분석기의 판정 결과 ROLEExecutive Summary → 국가별 상세 → 액션 아이템 순으로 서사 구성 OUT사람이 읽는 구조화 보고서(대시보드 텍스트의 원천)

🔔 law-amendment-monitor 감시

이전 법령 스냅샷과 현재를 비교해 최근 개정을 감지하고 재분석을 촉발("새로고침").

IN저장된 이전 스냅샷 + 현재 검색 결과, 트리거 키워드(새로고침/refresh) ROLE변경 감지 시 갭 재분석을 발화 → 데이터 최신성 유지 OUT변경 감지 알림 및 갱신 대상 목록

✅ law-verification-agent 검증

완성된 data/*.json의 모든 숫자·개정·판례·링크를 1차 출처와 대조해 신뢰도를 스탬프 (자세히는 §7).

INdata/*.json 파일들, 트리거("법령 검증"/"verify laws") ROLE파일별로 사실 목록화 → 출처 대조 → ✅확인/⚠️수정/❓미확인 분류 → 안전한 수정 반영 OUT각 JSON에 verification 블록(신뢰도·발견 이슈) 기록, 필요 시 값 교정
중요 — 이 에이전트들은 전부 "데이터를 만드는 도구"입니다. 완성된 웹앱은 이들이 만든 data/*.json을 꺼내 쓰기만 하며, 사용자가 앱을 쓸 때 에이전트가 매번 돌지 않습니다.

4. 오케스트레이터의 6단계 지휘 파이프라인 Orchestration

오케스트레이터의 본문에는 "엄격한 순서(Strict Order)"로 하위 에이전트를 부르는 파이프라인이 못 박혀 있습니다. 사람이 매번 지시하지 않아도 이 순서대로 자동 진행됩니다.

Step 1 · 국가 선택

분석할 국가를 확인·정규화(한국어/영어 혼용 허용). 미지정 시 사용자에게 질문.

Step 2 · 법령 수집 → labor-law-researcher dispatch

국가별로 최신 법령·개정·최저임금·근로시간을 출처 URL과 함께 수집. 에이전트 부재 시 오케스트레이터가 직접 수행.

Step 3 · HR 제도 검토 → hr-policy-structurer dispatch

현행 HR 정책을 Step 2의 법령 카테고리에 매핑. 자료 없으면 업계 벤치마크로 진행.

Step 4 · 갭 분석 → compliance-gap-analyzer dispatch

Step 2·3 출력을 넘겨 항목별 🔴/🟡/🟢 판정 + 개선 권고·우선순위 도출.

Step 5 · 리포트 구성 → gap-analysis-reporter dispatch

Executive Summary·국가별 상세·액션 아이템으로 서사화.

Step 6 · 인터랙티브 HTML/데이터 산출

법정 기준(좌) vs 현행 제도 입력(우) 2단 비교 구조의 자립형 HTML 생성. 개정 타임라인·저장/불러오기·인쇄 기능 포함. 이 산출물이 나중에 Streamlit 앱 + data/*.json으로 정착됨.

"dispatch"가 뭔가요? — 오케스트레이터가 각 하위 에이전트를 Agent(Task) 도구로 호출하는 것입니다. 각 하위 에이전트는 독립된 컨텍스트에서 자기 시스템 프롬프트만 갖고 실행되고, 결과만 오케스트레이터에게 돌려줍니다. 그래서 앞 단계 산출물이 뒤 단계의 입력이 되는 조립 라인이 됩니다.

실제로 사용자가 하는 일은 이 한 줄

> 한국과 일본의 노동법 컴플라이언스 리포트를 만들어줘

# → Claude가 description을 보고 compliance-orchestrator를 선택·실행
# → 오케스트레이터가 Step 1~6을 자동으로 진행하며 하위 에이전트를 차례로 호출

5. 수집한 데이터를 저장하는 두 곳 Where Data Lives

에이전트가 수집·정리한 결과는 ① 앱이 쓰는 JSON과 ② 에이전트가 다음 실행에서 재사용하는 메모리 두 군데에 저장됩니다.

5-1. data/<국가_도시>.json — 앱이 실제로 읽는 법령 데이터

한 국가-도시당 파일 하나. 현재 8개국(휴스턴·베이징·도쿄·모스크바·암스테르담·카르타헤나·두마이·구르가온)이 있습니다. 아래는 실제 japan_tokyo.json의 구조를 발췌·정리한 것입니다.

}

standards = 숫자 비교의 기준

주당 시간·연차·해고예고·최저임금 같은 단일 법정 수치. 룰 엔진이 사용자 입력과 직접 대소 비교합니다.

standard_checks / country_specifics = 구조화 점검

휴게시간·주휴일·36협정처럼 항목마다 type·threshold·fail_level·applies_if를 담아, 코드 수정 없이 데이터만으로 판정 규칙을 확장합니다.

6. 저장값 vs 공식 기준 — 비교·판정 로직 Rule Engine

개발 단계에서 갭 분석기가 하던 "법정 vs 현행 비교"를, 운영 단계에서는 rules.py의 결정론적 함수가 대신합니다. LLM 없이 순수 규칙으로 판정합니다.

6-1. 판정 4단계 레벨

high  위반/미달 가능성 큼 medium  주의 ok  적합 info  수동 확인 필요

6-2. 핵심 비교 — 숫자 대소 판정

사용자 입력값과 standards의 법정 수치를 직접 비교합니다. 아래는 실제 rules.py의 "연차휴가" 판정 로직입니다.

rules.py — evaluate() 중 연차휴가
legal_leave = std.get("annual_leave_min_days")   # 저장된 공식 기준
user_leave  = inputs.get("annual_leave")          # 사용자 입력(우리 회사)

if legal_leave == 0:
    # 미국 텍사스 등 법정 연차 의무 없음 → info(수동 확인)
    level = "info"
elif user_leave < legal_leave:
    # 미달 → high(위반)
    level = "high"   # "연차 {user}일 < 법정 최소 {legal}일 → 미달분만큼 위반"
else:
    level = "ok"     # 적합

같은 방식으로 정규 근로시간·최대 근로시간·해고 예고기간·최저임금을 각각 비교합니다. 값이 null(예: 일본의 주당 상한 없음)이면 기계적으로 판정하지 않고 info로 돌려 수동 확인을 유도합니다 — 잘못된 자동 판정을 피하는 안전장치입니다.

6-3. 구조화 점검 — 데이터로 규칙을 확장

standard_checks[] 항목은 type에 따라 판정 방식이 갈립니다. 코드를 고치지 않고 JSON에 항목만 추가하면 새 점검이 생깁니다.

type비교 방식예
number_min입력 ≥ threshold 이면 ok, 미만이면 fail_level휴게시간 ≥ 60분
number_max입력 ≤ threshold 이면 ok, 초과면 fail_level수습기간 ≤ 상한
boolean"예"→ok / "아니오"→fail / 그외→info36협정 체결 여부
choice선택지별로 사전 정의된 레벨 매핑임금 지급주기
posture숫자 기준이 불확실할 때 자세/이행 여부만 확인(오판 방지)해석 여지 큰 항목

6-4. 직원 수 조건 — applies_if

취업규칙·고충처리·여성위원회처럼 일정 규모 이상에만 적용되는 규제는 applies_if로 처리합니다. 조건에 안 맞으면 판정 대신 "규모 기준 미해당(info)"으로 안내합니다.

rules.py — check_applies()
cond = chk.get("applies_if")          # 예: {field:"headcount", op:">=", value:50}
cur  = context.get(cond["field"])       # 사용자가 입력한 직원 수
if op == ">=": return cur >= cond["value"]  # 50명 이상일 때만 이 점검 적용

6-5. 분쟁 위험 렌즈 — dispute_risk

단순 법 위반 여부와 별개로, 그 나라에서 실제 소송·노사분쟁이 잦은 쟁점(부당해고·미지급 초과수당·퇴직금 등)에는 dispute_risk:"high" 태그가 붙습니다. 룰 엔진은 이 태그를 판정 결과에 그대로 실어 "법적으로는 애매해도 분쟁 리스크가 큰 영역"을 부각합니다.

6-6. 주관식은? — 앱이 프롬프트만 생성

숫자로 판정 못 하는 질문은, 앱이 저장된 법령 요약 + 우리 회사 입력을 묶어 LLM용 프롬프트를 자동 생성합니다(실행은 사용자가 복붙). 런타임에 앱이 직접 LLM을 부르지 않는다는 원칙을 지키는 절충입니다.

compliance_app.py — build_llm_prompt() (요지)
return f"""당신은 {country}({city})의 노동법 컴플라이언스 전문가입니다.
[현지 법령 요약 · 기준시점 {as_of}]
- 정규/최대 근로시간, 최저임금, 연차, 해고 예고, 국가 특유 제도, 최근 개정...
[우리 회사 현행 제도]  - 정량: {입력}  - 특유제도 대응: {입력}
[질문] {question}"""

7. 데이터를 믿을 수 있게 — 법령 검증 루프 Verification

조사·저장이 끝났다고 바로 배포하지 않습니다. law-verification-agent가 빌드 타임에 모든 하드 넘버를 1차 출처와 대조합니다.

로드 & 매핑

파일의 모든 검증 대상 사실(최저임금·법정일수·기여율·개정 상태·판례·출처)을 목록화.

검색 & 대조

WebSearch+WebFetch로 1차 출처(정부·관보·법원) 확인. 최저임금과 12개월 내 시행 항목을 우선.

분류

✅확인 / ⚠️낡음·오류(정확값 기록) / ❓미확인 으로 표시. 공포일 vs 시행일 구분.

안전한 교정

명백히 지난 값만 수정(예: 시행일 지났는데 "예정" → "시행 중"). 애매하면 issues_found에 기록하고 사용자 확인 요청.

스탬프

파일 최상단 verification 블록에 신뢰도(high/medium/low)와 발견 이슈를 정직하게 남김.

data/*.json 에 남는 verification 블록
"verification":{
  "last_verified":"2026-06-...", "verified_by":"law-verification-agent",
  "confidence":"high",                        # 하드넘버·최근시행 항목 모두 1차출처 확인 시
  "issues_found":[{"field":"standards.min_wage.amount","problem":"...","action":"수정함"}],
  "notes":"무엇을 확인했고 무엇이 남았는지 한 줄 요약"
}
원칙 — 🔴/🟡 판정을 유발하는 숫자는 반드시 1차·2차 출처로 추적되어야 하며, 확인 불가하면 거짓 "high"보다 정직한 "medium/low"를 택합니다. 검증 못 한 판례도 지우지 않고 이슈로 남깁니다.
